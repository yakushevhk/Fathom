  <section id="profiles-deep">
    <h2>Built-in Profiles Deep Dive</h2>

    <h3>hunter</h3>
    <p>
      The <strong>hunter</strong> profile is optimized for contact harvesting at maximum volume. It forces
      <code>max_agents = 6</code>, keeps temperature at 0.4 for consistent extraction, and always includes
      <code>extract_contacts</code>, <code>save_contacts</code>, and <code>verification</code> in the tool chain.
    </p>
    <div class="code-card">
      <div class="code-header"><span class="code-lang">hunter.toml</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`[profile]
name = "hunter"
description = "Harvest maximum verified contacts fast"
prompt = """
You are a contact-harvesting agent. Your sole objective is to find and
verify as many contacts as possible. Prioritize volume but never save
unverified contacts. Always run email syntax + MX checks before saving.
For each company, search for C-suite, VP Engineering, and Head of Product.
"""
temperature = 0.4
max_agents = 6
max_depth = 2
deny_tools = ["git_push"]\`}`}} /></pre>
    </div>
    <div class="code-card code-card--gap">
      <div class="code-header"><span class="code-lang">usage</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`parallel-research run --profile hunter "Find engineering leaders at YC W24 companies"\`}`}} /></pre>
    </div>
    <p>
      What changes: the agent spawns up to 6 parallel sub-agents, each tackling a slice of the search space.
      The system prompt steers toward breadth — search every company, extract every visible contact, verify
      email and phone, and save immediately. The <code>git_push</code> denial prevents accidental code pushes
      when the research folder is a git repo.
    </p>

    <h3>analyst</h3>
    <p>
      The <strong>analyst</strong> profile is a read-only deep researcher. It denies <code>save_contacts</code>
      and <code>git_push</code>, so no side effects occur. Temperature is set to 0.3 for precise, cited output.
      Best for competitive analysis, technical deep-dives and due diligence.
    </p>
    <div class="code-card">
      <div class="code-header"><span class="code-lang">analyst.toml</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`[profile]
name = "analyst"
description = "Deep, cited, read-only research"
prompt = """
You are a research analyst. Produce thoroughly sourced findings with
inline citations. Every claim MUST link to a source URL. Cross-reference
facts across multiple sources. Flag conflicting information explicitly.
Never save contacts or modify external systems — you are read-only.
"""
model = "gpt-4o"
temperature = 0.3
max_agents = 4
max_depth = 3
max_iterations = 30
deny_tools = ["save_contacts", "git_push"]\`}`}} /></pre>
    </div>
    <div class="code-card code-card--gap">
      <div class="code-header"><span class="code-lang">usage</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`parallel-research run --profile analyst "Evaluate the competitive landscape of vector databases"\`}`}} /></pre>
    </div>
    <p>
      What changes: the agent uses <code>max_iterations = 30</code> for longer exploration chains and
      <code>max_depth = 3</code> to allow deeper sub-agent nesting. The prompt forces citation of every
      claim and explicit flagging of contradictions.
    </p>

    <h3>validator</h3>
    <p>
      The <strong>validator</strong> profile is a single-pass contact cleaner. It takes an existing contact
      list, verifies every entry, and enriches what it can. It denies <code>spawn_agent</code> so it runs
      as a focused, single-process agent.
    </p>
    <div class="code-card">
      <div class="code-header"><span class="code-lang">validator.toml</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`[profile]
name = "validator"
description = "Verify and enrich existing contacts"
prompt = """
You are a contact validation agent. You have been given an existing
contact list. For each contact: verify the email (syntax + MX + SMTP),
normalize the phone to E.164, check the social profile URL, and enrich
with any missing fields (title, company, LinkedIn). Mark invalid entries
but do not delete them. Return a clean, enriched list.
"""
temperature = 0.2
max_agents = 1
max_depth = 1
max_iterations = 50
deny_tools = ["spawn_agent"]\`}`}} /></pre>
    </div>
    <div class="code-card code-card--gap">
      <div class="code-header"><span class="code-lang">usage</span></div>

    </div>
    <p>
      What changes: no sub-agents spawn — the entire validation runs in a single agent loop.
      <code>max_iterations = 50</code> gives the agent room to verify large lists without hitting the limit.
      Temperature is the lowest of all profiles (0.2) for deterministic, mechanical work.
    </p>

  {/* ============ PROFILE INHERITANCE ============ */}
  <section id="profile-inheritance">
    <h2>Profile Inheritance &amp; Resolution</h2>
    <p>
      When a profile omits a field, the runtime resolves it from <code>config.toml</code>. The resolution
      order is: profile TOML → <code>[agent]</code> section → built-in defaults. This means a minimal
      profile only needs a <code>prompt</code> — everything else works out of the box.
    </p>
    <div class="mini-table-wrap">
      <table class="mini-table">
        <thead><tr><th>Resolution</th><th>Source</th><th>Example</th></tr></thead>
        <tbody>
          <tr><td>1 — Profile</td><td>Profile TOML file</td><td><code>temperature = 0.3</code> in analyst.toml</td></tr>
          <tr><td>2 — Config</td><td><code>~/.parallel-research/config.toml</code></td><td><code>[agent] temperature = 0.7</code></td></tr>
          <tr><td>3 — Built-in</td><td>Compiled defaults</td><td><code>temperature = 0.7</code></td></tr>
        </tbody>
      </table>
    </div>
    <p>
      The <code>prompt</code> field is <em>appended</em> to the base system prompt, not a replacement. This
      means your profile prompt adds role-specific instructions on top of the standard safety, grounding
      and tool-use instructions that every agent receives.
    </p>
  </section>

  {/* ============ GROUNDING RULES IN DETAIL ============ */}
  <section id="grounding-detail">
    <h2>Grounding Rules in Detail</h2>
    <p>
      The four grounding rules are the difference between spam and signal. Each rule has a concrete
      before/after example showing how it transforms the draft.
    </p>

    <h3>Rule A — Ground in facts</h3>
    <p>
      The writer only uses things the tools actually returned. If a web search found a Series B announcement
      and a job posting for 6 engineers, those facts — and only those — go into the draft. Every claim
      is traceable to a source URL.
    </p>
    <div class="code-card">
      <div class="code-header"><span class="code-lang">before (no grounding)</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`Hi Ann, I noticed your company has been growing rapidly and is probably
looking for solutions to scale its infrastructure.\`}`}} /></pre>
    </div>
    <div class="code-card code-card--gap">
      <div class="code-header"><span class="code-lang">after (grounded in facts)</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`Hi Ann, saw that Acme closed its Series B last month (TechCrunch, Feb 12)
and is hiring 6 platform engineers (careers page). Given your team's
Rust stack and the scaling challenges that come with a 3x headcount bump,
wanted to share how we cut our own infra costs by 40%.\`}`}} /></pre>
    </div>

    <h3>Rule B — Never fabricate</h3>
    <p>
      The iron rule: no invented facts, contacts, dates or sources. If a fact is missing, the draft either
      says so explicitly or opens with what is known. The model is penalized in the system prompt for
      hallucinating — fabrications cause an immediate generation restart.
    </p>
    <div class="code-card">
      <div class="code-header"><span class="code-lang">before (fabricated)</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`Hi Ann, congratulations on Acme's recent $50M Series B led by Sequoia!
I saw your recent talk at RustConf 2025 about microservices.\`}`}} /></pre>
    </div>
    <div class="code-card code-card--gap">
      <div class="code-header"><span class="code-lang">after (honest)</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`Hi Ann, saw that Acme closed a funding round last month — congrats to
the team. I couldn't find details on the lead investor, but the scale
of your recent engineering hires suggests significant growth ahead.\`}`}} /></pre>
    </div>

    <h3>Rule C — Layer memory</h3>
    <p>
      At depth 0 the agent receives a <strong>memory digest</strong> — a compact summary of all prior
      interactions with this contact or company. Past touches, prior conversations and known role changes
      surface automatically, so repeat outreach is continuous, not from zero.
    </p>
    <div class="code-card">
      <div class="code-header"><span class="code-lang">before (no memory)</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`Hi Ann, I wanted to introduce our platform and see if there's a fit.\`}`}} /></pre>
    </div>
    <div class="code-card code-card--gap">
      <div class="code-header"><span class="code-lang">after (memory-aware)</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`Hi Ann, following up on our chat from January — you mentioned the
migration to Rust was your Q1 priority. Now that it's Q2, I noticed
Acme is hiring platform engineers, which suggests you've made progress.
Curious how the rollout went and whether our earlier benchmarks would
still be useful.\`}`}} /></pre>
    </div>
    <p>
      The memory digest includes: contact name, company, known role (and any role changes), last interaction
      date, previous topics discussed, and any facts stored from prior runs. This data is injected as a
      frozen prompt block at depth 0 to keep the prefix cache warm.
    </p>

    <h3>Rule D — Human approval</h3>
    <p>
      Side effects wait for an explicit yes. The agent drafts, then pauses. In the TUI the operator presses
      <code>y</code> to approve or <code>n</code> to reject. Via API, a <code>POST /sessions/:id/approve</code>
      call is required. Nothing ships to CRM, no emails are sent, no files are modified until a human says go.
    </p>
    <p>
      This means you can run <code>--profile hunter</code> to generate 50 personalized emails, review each
      one in the batch, and only approve the ones that pass your quality bar.
    </p>
  </section>

  {/* ============ ROLE-BASED MODEL ROUTING ============ */}
  <section id="role-routing">
    <h2>Role-Based Model Routing</h2>
    <p>
      The <code>[agent].role_models</code> table in <code>config.toml</code> lets you assign different LLMs
      to different agent roles. This is the primary cost optimization lever: use expensive models where
      prose quality matters, and cheap models everywhere else.
    </p>
    <div class="code-card">
      <div class="code-header"><span class="code-lang">config.toml</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`[agent]
# Default model for all roles
model = "gpt-4o-mini"

# Override specific roles
[agent.role_models]
writer = "gpt-4o"            # best prose quality
researcher = "deepseek-v3"   # cheap, good at extraction
analyst = "claude-3.5-sonnet" # strong reasoning
verifier = "gpt-4o-mini"     # simple checks, keep it cheap
coordinator = "gpt-4o"       # planning needs strong model

[llm]
fast_model = "gpt-4o-mini"   # high-volume extraction & parsing\`}`}} /></pre>
    </div>

    <h3>How role_models works</h3>
    <p>
      When the coordinator spawns a sub-agent, it assigns a role based on the sub-task type. The runtime
      checks <code>[agent.role_models]</code> first; if a role-specific model is set, that model is used.
      Otherwise it falls back to <code>[agent].model</code>.
    </p>
    <div class="mini-table-wrap">
      <table class="mini-table">
        <thead><tr><th>Role</th><th>Tasks</th><th>Recommended model tier</th></tr></thead>
        <tbody>
          <tr><td><code>coordinator</code></td><td>Planning, decomposition, synthesis</td><td>Strong reasoning (GPT-4o, Claude Sonnet)</td></tr>
          <tr><td><code>researcher</code></td><td>Web search, page scraping, OSINT</td><td>Cheap + fast (DeepSeek, GPT-4o-mini)</td></tr>
          <tr><td><code>analyst</code></td><td>Cross-referencing, fact-checking</td><td>Strong reasoning (Claude Sonnet, GPT-4o)</td></tr>
          <tr><td><code>writer</code></td><td>Personalized outreach drafts</td><td>Best prose (GPT-4o, Claude Opus)</td></tr>
          <tr><td><code>verifier</code></td><td>Email/phone/social verification</td><td>Cheap (GPT-4o-mini, local models)</td></tr>
        </tbody>
      </table>
    </div>

    <h3>fast_model for high-volume extraction</h3>
    <p>
      The <code>llm.fast_model</code> setting is used for tasks that need speed over quality: parsing
      HTML, extracting structured JSON from pages, classifying page types, normalizing data. These calls
      happen hundreds of times per session, so a cheap model (GPT-4o-mini, Gemini Flash) saves significant
      cost without affecting output quality.
    </p>

    <h3>Cost optimization strategies</h3>
    <div class="check-list">
      <div class="check-item"><span class="check-mark">✓</span><span>Use <code>fast_model</code> for all extraction and parsing — this is the biggest win</span></div>
      <div class="check-item"><span class="check-mark">✓</span><span>Keep the coordinator on a strong model — bad planning wastes more than it saves</span></div>
      <div class="check-item"><span class="check-mark">✓</span><span>Use a strong model for the writer — prose quality is the deliverable</span></div>

    <h2>Draft Quality Controls</h2>
    <p>
      Fathom has multiple layers of quality control to ensure drafts are accurate, sourced, and safe
      to send. These controls run automatically — no configuration needed.
    </p>

    <h3>Hallucination avoidance</h3>
    <p>
      The system prompt contains an explicit anti-hallucination directive. The writer is instructed to
      only reference facts that appear in the tool results provided to it. If a fact is not in the context,
      the writer either omits it or uses a hedging phrase ("I couldn't verify..."). The runtime also
      validates that any URL cited in the draft actually appeared in the research results.
    </p>

    <h3>Source citation requirements</h3>
    <p>
      Every factual claim in a draft must trace back to a tool result. The writer uses inline references:
    </p>
    <div class="code-card">
      <div class="code-header"><span class="code-lang">citation format</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`"Acme raised $50M in Series B" → sourced from: web_search result #3 (TechCrunch)
"Currently hiring 6 engineers" → sourced from: web_fetch of careers page
"CTO since 2022" → sourced from: LinkedIn profile scrape\`}`}} /></pre>
    </div>
    <p>
      In the TUI, each claim in the draft can be traced back to its source tool call in the Log panel.
    </p>

    <h3>Confidence thresholds</h3>
    <p>
      The writer assigns implicit confidence levels to claims based on source quality. The runtime enforces
      these rules:
    </p>
    <div class="mini-table-wrap">
      <table class="mini-table">
        <thead><tr><th>Confidence</th><th>Source type</th><th>Draft behavior</th></tr></thead>
        <tbody>
          <tr><td>High</td><td>Official page, press release, SEC filing</td><td>State as fact</td></tr>
          <tr><td>Medium</td><td>News article, LinkedIn, job posting</td><td>State with attribution</td></tr>
          <tr><td>Low</td><td>Single unverified source, social post</td><td>Hedge: "appears to", "according to"</td></tr>
          <tr><td>Unverified</td><td>No corroborating source found</td><td>Omit from draft or flag as unverified</td></tr>
        </tbody>
      </table>
    </div>
