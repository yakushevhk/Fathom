  <section>
    <h2 id="multi-process" data-i18n="docsArchitecture.multiProcess">Multi-Process</h2>
    <p>By default all agents run in one process as tokio tasks. The hidden <code>fathom worker …</code> mode is reserved for coordinator-managed process isolation and is not a user-facing command.</p>

    <div class="code-block">
      <div class="code-header"><span class="code-lang">unix socket IPC</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`Coordinator (process 1)
    │  Unix socket IPC (JSON lines)
    ├──spawn──► Worker (process 2)  ── agent_id_1
    ├──spawn──► Worker (process 3)  ── agent_id_2
    └──spawn──► Worker (process 4)  ── agent_id_3

events: progress · tool-call · completion\`}`}} /></pre>
    </div>

    <ul class="prop-list">
      <li><strong>kill_on_drop</strong> — worker handles are spawned with <code>kill_on_drop(true)</code>: a dropped handle terminates the child, so no orphaned processes survive a cancelled run.</li>
      <li><strong>30 s startup timeout</strong> — a worker must open its socket within 30 seconds or it is reaped and reported.</li>
      <li><strong>SQLite WAL mode</strong> — concurrent access from every process against one database, pool of 4 connections.</li>
      <li><strong>Isolation</strong> — one agent crashing never takes down the fleet; resource limits apply per process.</li>
    </ul>
  </section>

  <section id="security">
    <h2>Security Architecture</h2>
    <p>
      Fathom has 12 security layers that run at different points in the agent lifecycle.
      These are not optional features — they are always active and cannot be disabled.
    </p>

    <h3>All 12 security layers</h3>
    <div class="mini-table-wrap">
      <table class="mini-table">
        <thead><tr><th>#</th><th>Layer</th><th>When it runs</th><th>Description</th></tr></thead>
        <tbody>
          <tr><td>1</td><td>SSRF guard</td><td>Before HTTP requests</td><td>Blocks requests to internal/private network addresses</td></tr>
          <tr><td>2</td><td>Prompt injection detection</td><td>On all tool inputs</td><td>12 regex + heuristic patterns catch prompt injection attempts</td></tr>
          <tr><td>3</td><td>Secret scanning</td><td>On all tool outputs</td><td>8 secret types detected and redacted before they enter context</td></tr>
          <tr><td>4</td><td>Destructive command blocking</td><td>Before exec</td><td>8 shell patterns blocked (rm -rf /, mkfs, fork bombs, etc.)</td></tr>
          <tr><td>5</td><td>Doom-loop detection</td><td>Before each LLM call</td><td>3 identical tool calls in a row stops the loop</td></tr>
          <tr><td>6</td><td>Role-based deny list</td><td>Before tool execution</td><td>Profile-level tool denials (e.g. analyst can't save_contacts)</td></tr>
          <tr><td>7</td><td>Approval flow</td><td>Before side effects</td><td>Human-in-the-loop for approval_tools via TUI or API</td></tr>
          <tr><td>8</td><td>PreToolUse hooks</td><td>Before tool execution</td><td>External subprocess hooks can allow, deny or enrich tool calls</td></tr>
          <tr><td>9</td><td>Tool output truncation</td><td>After tool execution</td><td>50 KB / 2000 lines per output; overflow persisted to disk</td></tr>
          <tr><td>10</td><td>Protected surfaces</td><td>On file operations</td><td>config.toml, memory.db, .research.db cannot be modified by agents</td></tr>
          <tr><td>11</td><td>API key authentication</td><td>On HTTP requests</td><td>Non-loopback binds require FATHOM_API_KEYS</td></tr>
          <tr><td>12</td><td>Rate limiting</td><td>On HTTP requests</td><td>Per-key rate limits on the server API</td></tr>
        </tbody>
      </table>
    </div>

    <h3>SSRF guard</h3>
    <p>
      The SSRF guard intercepts every HTTP request before it leaves the process. It resolves the target hostname
      and checks the resulting IP against a blocklist: <code>10.0.0.0/8</code>, <code>172.16.0.0/12</code>,
      <code>192.168.0.0/16</code>, <code>127.0.0.0/8</code>, <code>169.254.0.0/16</code>, <code>::1</code>,
      <code>fc00::/7</code>. DNS rebinding is mitigated by resolving before connecting and verifying the
      resolved address before the TCP handshake completes.
    </p>

    <h3>Prompt injection defense</h3>
    <p>
      Twelve patterns detect prompt injection attempts in tool outputs and user inputs:
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">detected patterns</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`1.  "ignore previous instructions"
2.  "you are now a ..."
3.  "system: " or "[system]" prefix injection
4.  Base64-encoded instruction blocks
5.  "disregard all prior"
6.  Invisible Unicode direction overrides (BiDi)
7.  Markdown link injection with javascript: URIs
8.  Nested tool_call JSON in tool outputs
9.  "IMPORTANT:" overrides in scraped page content
10. Repeated newlines followed by instruction blocks
11. XML/CDATA wrapping to break output parsing
12. Unicode homoglyph substitution in keywords\`}`}} /></pre>
    </div>
    <p>
      When a pattern is detected, the output is sanitized and a warning is logged. The agent receives
      a cleaned version of the content.
    </p>

    <h3>Secret scanning</h3>
    <p>
      Every tool output passes through a secret scanner before entering the context window. Eight types
      are detected and redacted with a <code>[REDACTED:type]</code> marker:
    </p>

  {/* ============ CONTEXT WINDOW MANAGEMENT ============ */}
  <section id="context-window">
    <h2>Context Window Management</h2>
    <p>
      The context window is the most constrained resource in any agent system. Fathom manages it through
      five stages, each progressively more aggressive. The goal: keep the agent productive without losing
      critical information.
    </p>

    <h3>The five stages in detail</h3>
    <div class="steps">
      <div class="step-card">
        <div class="step-num">01</div>
        <div>
          <div class="step-title">BPE token counting</div>
          <p class="step-desc">Exact counting with tiktoken cl100k_base; CJK-aware heuristic fallback for non-Latin scripts. The counter runs before every LLM call. You cannot manage what you estimate wrong — this is why approximate char/4 counting is not used.</p>
        </div>
      </div>
      <div class="step-card">
        <div class="step-num">02</div>
        <div>
          <div class="step-title">Tool result truncation</div>
          <p class="step-desc">Each tool output is capped at <code>tool_output_max_bytes</code> (default 50 KB) or 2000 lines. The per-turn budget is <code>turn_budget_bytes</code> (default 200 KB). Overflow is persisted to disk with a pointer, so the agent can reference it later without bloating the context.</p>
        </div>
      </div>
      <div class="step-card">
        <div class="step-num">03</div>
        <div>
          <div class="step-title">Micro-compaction</div>
          <p class="step-desc">Deduplicate tool results by content hash and prune older outputs that have been superseded. This is fast and deterministic — no LLM call required. Runs automatically when context fills up.</p>
        </div>
      </div>
      <div class="step-card">
        <div class="step-num">04</div>
        <div>
          <div class="step-title">Full compaction (Hermes-style)</div>
          <p class="step-desc">An LLM summarizes the middle of the conversation. The context becomes: head (system prompt + first messages) + summary (compressed middle) + tail (recent messages). This is the only stage that costs tokens.</p>
        </div>
      </div>
      <div class="step-card">
        <div class="step-num">05</div>
        <div>
          <div class="step-title">Anti-thrashing cooldown</div>
          <p class="step-desc">After a full compaction pass that fails to free enough space, the runtime enters a cooldown period instead of compacting again immediately. This prevents the pathological case of spending all tokens on compaction without making progress.</p>
        </div>
      </div>
    </div>

    <h3>Configuration</h3>
    <div class="mini-table-wrap">
      <table class="mini-table">
        <thead><tr><th>Setting</th><th>Default</th><th>Description</th></tr></thead>
        <tbody>
          <tr><td><code>context_window</code></td><td>model default</td><td>Maximum tokens for the model (128K or 256K)</td></tr>
          <tr><td><code>compact_threshold</code></td><td>0.50</td><td>Trigger compaction at this fraction of context_window</td></tr>
          <tr><td><code>tool_output_max_bytes</code></td><td>50 KB</td><td>Per-tool output cap</td></tr>
          <tr><td><code>turn_budget_bytes</code></td><td>200 KB</td><td>Total per-turn budget for all tool outputs</td></tr>
        </tbody>
      </table>
    </div>

    <h3>Window profiles</h3>
    <p>
      Two profiles are available depending on the model's context window size:
    </p>
    <div class="mini-table-wrap">
      <table class="mini-table">
        <thead><tr><th>Profile</th><th>context_window</th><th>compact_threshold</th><th>Best for</th></tr></thead>
        <tbody>
          <tr><td><code>low</code></td><td>128K tokens</td><td>0.50 (64K)</td><td>GPT-4o-mini, Claude Haiku, cheaper models</td></tr>
          <tr><td><code>max</code></td><td>256K tokens</td><td>0.50 (128K)</td><td>Claude Sonnet, GPT-4o, Gemini Pro</td></tr>
        </tbody>
      </table>
    </div>
    <p>
      Long-term memory complements all of it: relevant facts arrive as a prompt digest instead of living
      in session context. This means the agent can "remember" thousands of facts without consuming context
      window space.
    </p>

  {/* ============ MULTI-PROCESS ARCHITECTURE ============ */}
  <section id="multiprocess-detail">
    <h2>Multi-Process Architecture</h2>
    <p>
      By default all agents run as tokio tasks within a single process. With <code>use_multiprocess = true</code>
      in <code>config.toml</code>, each sub-agent becomes its own OS process with full isolation.
    </p>

    <h3>How use_multiprocess works</h3>
    <div class="steps">
      <div class="step-card">
        <div class="step-num">01</div>
        <div>
          <div class="step-title">Coordinator spawns workers</div>
          <p class="step-desc">When process isolation is enabled, the coordinator may launch the hidden <code>fathom worker</code> mode as a child process; users should start work with <code>fathom run</code> or <code>fathom tui</code>.</p>
        </div>
      </div>
      <div class="step-card">
        <div class="step-num">02</div>
        <div>
          <div class="step-title">Unix socket connection</div>
          <p class="step-desc">Each worker connects back to the coordinator over a Unix domain socket. Messages are newline-delimited JSON (JSONL). The protocol supports: progress events, tool-call events, completion events, and error events.</p>
        </div>
      </div>
      <div class="step-card">
        <div class="step-num">03</div>
        <div>
          <div class="step-title">Independent agent loop</div>
          <p class="step-desc">Each worker runs its own complete agent loop: prompt building, LLM calls, tool execution, context management. It shares nothing with other workers except the SQLite database (WAL mode, 4-connection pool).</p>
        </div>
      </div>
      <div class="step-card">
        <div class="step-num">04</div>
        <div>
          <div class="step-title">Result collection</div>
          <p class="step-desc">When a worker finishes, it sends a completion event over the socket. The coordinator collects the result and feeds it into the synthesis step.</p>
        </div>
      </div>
    </div>

    <h3>Unix socket IPC protocol</h3>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">IPC message format</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`→ Coordinator → Worker:   {"type":"start","task":"...","tools":[...]}
← Worker → Coordinator:   {"type":"progress","agent_id":"...","msg":"searching..."}
← Worker → Coordinator:   {"type":"tool_call","tool":"web_search","args":{...},"ms":342}
← Worker → Coordinator:   {"type":"completion","agent_id":"...","result":"..."}
← Worker → Coordinator:   {"type":"error","agent_id":"...","error":"timeout"}\`}`}} /></pre>
    </div>

    <h3>kill_on_drop safety</h3>
    <p>
      Worker handles are wrapped in <code>tokio::process::Command::kill_on_drop(true)</code>. This means:
    </p>
    <ul class="prop-list">
      <li>If the coordinator process crashes, all workers are killed automatically by the OS.</li>
      <li>If a worker handle is dropped (cancelled task), the child process is terminated immediately.</li>
      <li>No orphaned worker processes can survive a cancelled run or a panic.</li>
      <li>A 30-second startup timeout ensures dead workers are reaped quickly.</li>
    </ul>

    <h3>When to use multi-process vs single-process</h3>
    <div class="mini-table-wrap">
      <table class="mini-table">
        <thead><tr><th>Aspect</th><th>Single-process (default)</th><th>Multi-process</th></tr></thead>
        <tbody>
          <tr><td>Overhead</td><td>Low — tokio tasks are lightweight</td><td>Higher — OS processes with IPC</td></tr>
          <tr><td>Isolation</td><td>Shared memory, one panic kills all</td><td>Full process isolation</td></tr>
          <tr><td>Resource limits</td><td>Per-task (soft)</td><td>Per-process (OS-enforced)</td></tr>
          <tr><td>Debugging</td><td>Harder to isolate issues</td><td>Easier — each worker has its own stderr</td></tr>
          <tr><td>Best for</td><td>Small swarms (≤4 agents), development</td><td>Large swarms (6+ agents), production</td></tr>
        </tbody>
      </table>
    </div>
  </section>
