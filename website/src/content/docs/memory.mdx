    <h2 data-i18n="docsMemory.searchTitle">Search that blends semantics and keywords</h2>
    <p data-i18n="docsMemory.searchSub">Memory search is a hybrid of semantic (vector) similarity and BM25 keyword matching:</p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">formula</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`score = 0.7·cosine_similarity + 0.3·bm25_normalized
final  = score × max(0, 1 − 0.01·days_old)\`}`}} /></pre>
    </div>
    <ul class="check-list">
      <li><strong>Semantic weight 0.7</strong> balances meaning over exact-match.</li>
      <li><strong>Temporal decay 0.01/day</strong> slowly fades older facts — recent wins.</li>
      <li><strong>top_k 5, min_score 0.25</strong> keep results tight and relevant.</li>
      <li>Offline TF-IDF embeddings (512-dim) when no API key is set — no network required.</li>
      <li data-i18n="docsMemory.cap.graph">Entity knowledge graph (memory_graph) for persons, companies, locations and typed relations</li>
    </ul>

    <p data-i18n="docsMemory.graphBody">

  {/* ============ GC ============ */}
  <section id="gc">
    <h2 data-i18n="docsMemory.gcTitle">Grows, then tidies itself</h2>
    <p data-i18n="docsMemory.gcBody">
      An automated garbage collector archives stale run-scoped facts after 30 days and compacts
      crowded (scope, key) groups of 200+ active rows into one. Nothing is ever hard-deleted —
      the archive is always recoverable.
    </p>
  </section>

  <section id="distill">
    <h2 data-i18n="docsMemory.distillTitle">Distillation</h2>
    <p data-i18n="docsMemory.distillBody">
      Distillation promotes run-scoped episode facts into durable agent-scope knowledge. When a research
      session completes, the distiller re-absorbs its run-facts through the full pipeline (validate, dedup,
      classify) but targets the agent scope instead of the run scope. Originals are archived. This way,
      facts discovered during a single session become permanent knowledge available to all future sessions
      — without manual copying. Run <code>fathom memory distill --session &lt;key&gt;</code> or
      let <code>gc_auto = true</code> handle it on a background timer.
    </p>
  </section>

  {/* ============ MEMORY TOOLS REFERENCE ============ */}
  <section id="tools-reference">
    <h2>Memory Tools Reference</h2>
    <p>
      Seven specialized tools let you read, write, search, link, and reason over memory.
      Each tool is available to agents during research and can also be invoked from the CLI or REST API.
    </p>

    {/* — memory (file-backed) — */}
    <h3 id="tool-memory"><code>memory</code> — File-backed CRUD</h3>
    <p>
      The primary tool for direct record management. Every action operates on a single memory record
      identified by its UUID. Records belong to a scope and carry a key, content, and metadata.
    </p>
    <table class="mini-table">
      <thead><tr><th>Action</th><th>Description</th><th>Example</th></tr></thead>
      <tbody>
        <tr><td><code>list</code></td><td>Return all active records in a scope, newest first.</td><td><code>fathom memory list --scope agent</code></td></tr>
        <tr><td><code>read</code></td><td>Fetch a single record by ID, including full history.</td><td><code>fathom memory get abc123</code></td></tr>
        <tr><td><code>add</code></td><td>Create a new record with optional key and tags.</td><td><code>fathom memory search "Enterprise pricing" --scope run</code></td></tr>
        <tr><td><code>update</code></td><td>Patch content or metadata on an existing record.</td><td><code>fathom memory get abc123 --follow full_history</code></td></tr>
        <tr><td><code>delete</code></td><td>Soft-delete (archive) a record. Recoverable via restore.</td><td><code>fathom memory nuke --scope run --yes</code></td></tr>
        <tr><td><code>archive</code></td><td>Explicitly archive without deleting — same effect as delete.</td><td><code>fathom memory gc --dry-run</code></td></tr>
        
      </tbody>
    </table>

    {/* — memory_absorb — */}
    <h3 id="tool-absorb"><code>memory_absorb</code> — Fact Absorption</h3>
    <p>
      The recommended way to store new knowledge. <code>memory_absorb</code> feeds raw text through the
      full absorb pipeline — validation, secret scanning, consolidation, classification, and edge creation —
      so you never store duplicates or secrets accidentally.
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">example</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`memory_absorb({
  scope: "agent",
  fact: "Stripe acquired Lemon Squeezy in March 2024 for merchant-of-record capabilities"
})\`}`}} /></pre>
    </div>
    <p>The pipeline executes these steps in order:</p>
    <div class="flow-list">
      <div class="flow-item">
        <div class="flow-index">1</div>
        <div class="flow-body">
          <div class="flow-title">Validate</div>
          <p class="flow-desc">Length must be 3–5000 characters. Fragments under 3 chars or gibberish are rejected with <code>ERR_TOO_SHORT</code>.</p>
        </div>
      </div>
      <div class="flow-item">
        <div class="flow-index">2</div>
        <div class="flow-body">
          <div class="flow-title">Secret Scan</div>
          <p class="flow-desc">Regex patterns detect API keys, JWTs, SSH private keys, and passwords. Matched tokens are redacted before storage.</p>
        </div>
      </div>
      <div class="flow-item">
        <div class="flow-index">3</div>
        <div class="flow-body">
          <div class="flow-title">Consolidate</div>
          <p class="flow-desc">Embeddings are computed and compared against existing facts. Cosine similarity ≥ 0.85 triggers a merge into the canonical record.</p>
        </div>
      </div>
      <div class="flow-item">
        <div class="flow-index">4</div>
        <div class="flow-body">
          <div class="flow-title">Classify</div>
          <p class="flow-desc">LLM (or heuristic fallback) decides: <code>new</code>, <code>duplicate</code>, <code>supersede</code>, <code>contradict</code>, <code>coexist</code>, or <code>related</code>.</p>
        </div>
      </div>
      <div class="flow-item">
        <div class="flow-index">5</div>
        <div class="flow-body">
          <div class="flow-title">Apply Verdict</div>
          <p class="flow-desc">New rows are inserted; superseded rows get a <code>supersedes</code> edge; contradictions both survive with a <code>contradicts</code> edge.</p>
        </div>
      </div>
    </div>
    <p>Typical response:</p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">json</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`{
  "status": "absorbed",
  "memory_id": "mem_8f3a2b",
  "classification": "new",
  "embedding_model": "tfidf-512",
  "edges_created": 0,
  "duplicates_merged": 0
}\`}`}} /></pre>
    </div>

    {/* — memory_search — */}
    <h3 id="tool-search"><code>memory_search</code> — Hybrid Search</h3>
    <p>
      Combines vector similarity (semantic) with BM25 keyword matching for robust retrieval.
      Results are ranked by a weighted score and filtered by <code>min_score</code>.
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">example queries</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`memory_search({ scope: "agent", query: "Stripe pricing tiers", top_k: 5 })
memory_search({ scope: "user", query: "CEO name and background", top_k: 3 })
memory_search({ scope: "all", query: "competitor analysis fintech", min_score: 0.3 })\`}`}} /></pre>
    </div>
    <p>Scoring formula in detail:</p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">formula</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`raw_score = semantic_weight × cosine(embedding_q, embedding_doc)
           + (1 − semantic_weight) × bm25_normalized(query, doc)

temporal  = max(0, 1 − temporal_decay × days_since_last_update)

final_score = raw_score × temporal × importance_boost\`}`}} /></pre>
    </div>
    <p>Example search result:</p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">json</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`{
  "results": [
    {
      "id": "mem_8f3a2b",
      "content": "Stripe acquired Lemon Squeezy in March 2024",
      "scope": "agent",
      "score": 0.87,
      "semantic_component": 0.91,
      "bm25_component": 0.78,
      "temporal_factor": 0.96,
      "importance": 1.0,
      "updated_at": "2024-03-15T10:30:00Z"
    }
  ],
  "total": 1,
  "query_time_ms": 12
}\`}`}} /></pre>
    </div>

    {/* — memory_digest — */}
    <h3 id="tool-digest"><code>memory_digest</code> — Context Digest</h3>
    <p>
      Generates a condensed memory block suitable for injection into system prompts. The digest
      pulls the most relevant memories for the current context, open TODOs, and recent records.
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">example</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`memory_digest({
  scope: "agent",
  topic: "outreach to fintech companies",
  max_tokens: 2000
})\`}`}} /></pre>
    </div>
    <p>The digest includes three sections:</p>
    <ul class="check-list">
      <li><strong>Relevant memories</strong> — top-K facts matching the topic, ranked by score.</li>
      <li><strong>Open TODOs</strong> — any records tagged as TODO that are still active.</li>
      <li><strong>Recent records</strong> — facts absorbed in the last 48 hours, regardless of topic.</li>
    </ul>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">output</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`## Memory Digest — "outreach to fintech companies"

### Relevant Facts
- [agent] Stripe acquired Lemon Squeezy (MoR) in March 2024 (score: 0.87)
- [agent] Plaid raised Series D at $13.4B valuation (score: 0.72)
- [user] Target contact: Jane Doe, VP Engineering at Plaid (score: 0.68)

### Open TODOs
- [run] Draft personalized email for Jane Doe referencing Plaid's API-first approach

### Recent (last 48h)
- [run] Plaid announced new Transfer product on 2024-03-14\`}`}} /></pre>
    </div>

    {/* — memory_boost — */}
    <h3 id="tool-boost"><code>memory_boost</code> — Adjust Importance</h3>
    <p>
      Lets you increase or decrease the importance multiplier of a specific memory record.
      Boosted facts rank higher in search results and digests. Importance is a float multiplier
      applied during scoring — default is <code>1.0</code>.
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">example</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`memory_boost({
  id: "mem_8f3a2b",
  importance: 2.0,
  reason: "Critical acquisition — cite in all Stripe outreach"
})\`}`}} /></pre>
    </div>
    <p>How importance affects ranking:</p>
    <table class="mini-table">
      <thead><tr><th>Importance</th><th>Effect</th><th>Use Case</th></tr></thead>
      <tbody>
        <tr><td><code>0.5</code></td><td>Half-weight — deprioritized in results</td><td>Background context, nice-to-know</td></tr>
        <tr><td><code>1.0</code></td><td>Normal weight (default)</td><td>Standard facts</td></tr>
        <tr><td><code>1.5</code></td><td>50% boost in ranking</td><td>Important client preferences</td></tr>
        <tr><td><code>2.0</code></td><td>Double weight — always surfaces first</td><td>Critical facts, must-cite knowledge</td></tr>
        <tr><td><code>3.0</code></td><td>Triple weight — pinned to top</td><td>Deal-breaking constraints, legal requirements</td></tr>
      </tbody>
    </table>

    {/* — memory_link — */}
    <h3 id="tool-link"><code>memory_link</code> — Typed Edges</h3>
    <p>
      Creates a directed, typed edge between two memory records. Edges let you express relationships
      like "this fact supersedes that one" or "these two facts are related."
    </p>
    <table class="mini-table">
      <thead><tr><th>Edge Type</th><th>Description</th><th>Example</th></tr></thead>
      <tbody>
        <tr><td><code>related_to</code></td><td>General semantic connection between two facts.</td><td>"Stripe pricing" ↔ "Stripe MoR acquisition"</td></tr>
        <tr><td><code>supersedes</code></td><td>Newer fact replaces an older one. Old is archived.</td><td>"Series D at $13.4B" supersedes "Series C at $8B"</td></tr>
        <tr><td><code>contradicts</code></td><td>Two facts conflict — both kept visible for review.</td><td>"Q1 revenue $5M" contradicts "Q1 revenue $3M"</td></tr>
        <tr><td><code>implements</code></td><td>One fact is a concrete implementation of another.</td><td>"Used Stripe Checkout v2" implements "Migrated to Stripe"</td></tr>
        <tr><td><code>extends</code></td><td>One fact adds detail or context to another.</td><td>"Jane is ex-Google" extends "Jane is VP Engineering"</td></tr>
        <tr><td><code>references</code></td><td>One fact cites or references another as a source.</td><td>"Market size $50B" references "Gartner 2024 report"</td></tr>
      </tbody>
    </table>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">example</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`memory_link({
  from_id: "mem_new_series_d",
  to_id: "mem_old_series_c",
  edge_type: "supersedes",
  note: "Valuation updated after Series D announcement"
})\`}`}} /></pre>
    </div>

  <section id="entity-graph-deep-dive">
    <h2>Entity Graph Deep Dive</h2>
    <p>
      The entity graph sits alongside the memory store and provides structured, queryable
      relationships between real-world entities. Unlike free-text memories, the graph enforces
      typed nodes and edges so you can traverse relationships programmatically.
    </p>

    <h3>Entity Types</h3>
    <table class="mini-table">
      <thead><tr><th>Type</th><th>Description</th><th>Common Attributes</th></tr></thead>
      <tbody>
        <tr><td><code>person</code></td><td>Individual humans — contacts, founders, executives.</td><td><code>role</code>, <code>company</code>, <code>email</code>, <code>linkedin</code></td></tr>
        <tr><td><code>company</code></td><td>Organizations — prospects, competitors, partners.</td><td><code>industry</code>, <code>hq</code>, <code>size</code>, <code>founded</code></td></tr>
        <tr><td><code>location</code></td><td>Geographic places — cities, countries, regions.</td><td><code>country</code>, <code>state</code>, <code>timezone</code></td></tr>
      </tbody>
    </table>

    <h3>Building a Relationship Map</h3>
    <p>
      Entities are connected through typed relations. The graph supports directional edges,
      so <code>person → works_at → company</code> is distinct from <code>company → employs → person</code>.
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">relationship model</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`person:Jane Doe  ──works_at──▶  company:Plaid
company:Plaid    ──located_in──▶  location:San Francisco
person:Jane Doe  ──knows──▶  person:John Smith
company:Plaid    ──competes_with──▶  company:Stripe
company:Stripe   ──acquired──▶  company:Lemon Squeezy\`}`}} /></pre>
    </div>

    <h3>Multi-Hop Queries</h3>
    <p>
      The real power of the graph emerges with multi-hop traversal. You can ask questions
      like "find all people who work at companies headquartered in Berlin" by following
      the <code>works_at</code> and <code>located_in</code> edges across two hops.
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">multi-hop example</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`// Hop 1: Find companies in Berlin
//   location:Berlin ←──located_in── company:N26
//   location:Berlin ←──located_in── company:Delivery Hero

// Hop 2: Find people at those companies
//   company:N26 ←──works_at── person:Max Tayenthal
//   company:Delivery Hero ←──works_at── person:Niklas Östberg

// Result: [Max Tayenthal, Niklas Östberg]\`}`}} /></pre>
    </div>

    <h3>Entity Deduplication</h3>
    <p>
      When the same entity is referenced from different sources (e.g., "Plaid" from a news article
      and "Plaid Inc." from a CRM export), the graph merges them automatically. Deduplication uses
      name normalization and fuzzy matching:
    </p>
    <ul class="check-list">
      <li><strong>Name normalization</strong> — Strips suffixes like Inc., Ltd., Corp. before comparison.</li>
      <li><strong>Fuzzy matching</strong> — Levenshtein distance ≤ 2 on normalized names triggers a merge candidate.</li>
      <li><strong>Attribute merging</strong> — Conflicting attributes are kept as arrays; non-conflicting ones are unioned.</li>
      <li><strong>Edge re-wiring</strong> — All edges from the duplicate entity are re-pointed to the canonical one.</li>
    </ul>

    <h3>Graph Visualization Concept</h3>
    <p>
      The graph can be visualized as a node-link diagram where each entity is a node and each
      relation is a typed, directed edge. Node size reflects connectivity (degree centrality)
      and edge thickness can encode relation strength or recency.
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">visualization pseudocode</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`nodes = graph.list_entities()
edges = graph.list_relations()

for node in nodes:
  draw_circle(
    x=node.x, y=node.y,
    radius=2 + log(node.degree),
    color=type_colors[node.type],  // person=blue, company=green, location=orange
    label=node.name
  )

for edge in edges:
  draw_arrow(
    from=edge.from, to=edge.to,
    style=edge_type_styles[edge.type],  // solid, dashed, dotted
    label=edge.type
  )\`}`}} /></pre>
    </div>
  </section>

  <section id="config-reference">
    <h2>Memory Configuration Reference</h2>
    <p>
      All memory behavior is controlled through the <code>[memory]</code> section of your
      <code>config.toml</code> configuration file. Every field has a sensible default
      so you only need to override what matters for your use case.
    </p>
    <table class="mini-table">
      <thead><tr><th>Field</th><th>Type</th><th>Default</th><th>Description</th></tr></thead>
      <tbody>
        <tr><td><code>enabled</code></td><td>bool</td><td><code>true</code></td><td>Master switch. When false, all memory tools return stub responses and nothing is persisted.</td></tr>
        <tr><td><code>db_path</code></td><td>string</td><td><code>~/.fathom/memory.db</code></td><td>Path to the SQLite database file. Created automatically on first run.</td></tr>
        <tr><td><code>embeddings</code></td><td>string</td><td><code>"auto"</code></td><td>Embedding backend: <code>auto</code> (OpenAI if key present, else TF-IDF), <code>openai</code>, or <code>tfidf</code>.</td></tr>
        <tr><td><code>semantic_weight</code></td><td>float</td><td><code>0.7</code></td><td>Weight for semantic similarity in hybrid search. BM25 gets <code>1 − semantic_weight</code>.</td></tr>
        <tr><td><code>top_k</code></td><td>int</td><td><code>5</code></td><td>Number of results returned by <code>memory_search</code> and <code>memory_digest</code>.</td></tr>
        <tr><td><code>min_score</code></td><td>float</td><td><code>0.25</code></td><td>Minimum final score for a result to be included. Filters noise.</td></tr>
        <tr><td><code>temporal_decay</code></td><td>float</td><td><code>0.01</code></td><td>Daily decay rate applied to older facts. At 0.01, a 100-day-old fact scores at 0.0 of its original.</td></tr>
        <tr><td><code>auto_digest</code></td><td>bool</td><td><code>true</code></td><td>Automatically inject a memory digest into the top-level agent's system prompt.</td></tr>
        <tr><td><code>llm_classify</code></td><td>bool</td><td><code>true</code></td><td>Use the LLM for absorb classification. When false, falls back to heuristic rules.</td></tr>
        <tr><td><code>rerank</code></td><td>bool</td><td><code>false</code></td><td>Enable a second-pass LLM reranker on search results. Adds latency but improves precision.</td></tr>
        <tr><td><code>gc_auto</code></td><td>bool</td><td><code>false</code></td><td>Automatically run GC (including distillation) after each session completes.</td></tr>
        <tr><td><code>gc_ttl_days</code></td><td>int</td><td><code>30</code></td><td>Run-scoped facts older than this are archived by the GC.</td></tr>
        <tr><td><code>gc_compact_above</code></td><td>int</td><td><code>200</code></td><td>When a (scope, key) group exceeds this many active rows, GC compacts them.</td></tr>
      </tbody>
    </table>

    <h3>Field Details</h3>
    <p><strong><code>enabled</code></strong> — The master kill switch. Set to <code>false</code> to disable all memory features without removing configuration. Useful for testing or CI environments where persistent state is undesirable.</p>
    <p><strong><code>db_path</code></strong> — SQLite is used for zero-dependency local storage. The database contains tables for memories, embeddings, entity graph nodes, entity graph edges, and metadata. You can point this to a shared volume for multi-machine setups, though SQLite's single-writer model may require WAL mode.</p>
    <p><strong><code>embeddings</code></strong> — Controls how text is vectorized for semantic search. <code>auto</code> checks for an <code>OPENAI_API_KEY</code> environment variable; if found, it uses <code>text-embedding-3-small</code> (1536-dim). Otherwise it falls back to a local TF-IDF model (512-dim) that works entirely offline. The <code>tfidf</code> and <code>openai</code> options force one backend regardless of environment.</p>
    <p><strong><code>semantic_weight</code></strong> — Balances meaning vs. exact keywords. A higher value (e.g., 0.85) favors semantic understanding — good for natural-language queries. A lower value (e.g., 0.5) favors keyword matching — better for exact product names, acronyms, or codes. The default 0.7 works well for mixed workloads.</p>
    <p><strong><code>top_k</code></strong> and <strong><code>min_score</code></strong> — Control result volume and quality. <code>top_k</code> caps how many results come back; <code>min_score</code> filters out anything below the threshold. Raise <code>min_score</code> to 0.4+ for precision-critical tasks like legal or compliance research.</p>
    <p><strong><code>temporal_decay</code></strong> — Makes freshness matter. The formula is <code>max(0, 1 − decay × days_old)</code>. At the default 0.01, a fact is worth 90% after 10 days, 50% after 50 days, and 0% after 100 days. Set to 0.0 to disable decay entirely (all facts treated equally regardless of age).</p>
    <p><strong><code>auto_digest</code></strong> — When enabled, the system automatically generates and injects a memory digest into the top-level agent's system prompt before each run. This means the agent always has relevant context without explicit tool calls.</p>
    <p><strong><code>llm_classify</code></strong> — Controls whether the absorb pipeline uses an LLM to classify incoming facts (new, duplicate, supersede, contradict, coexist, related) or falls back to embedding-distance heuristics. The LLM path is more accurate but adds one API call per absorb.</p>
    <p><strong><code>rerank</code></strong> — When enabled, search results go through a second pass where the LLM reorders them by relevance to the original query. This adds latency (one extra LLM call) but can significantly improve result quality for complex or ambiguous queries.</p>
    <p><strong><code>gc_*</code></strong> fields — The garbage collector handles two tasks: (1) archiving run-scoped facts older than <code>gc_ttl_days</code>, and (2) compacting (scope, key) groups that exceed <code>gc_compact_above</code> active rows into a single canonical record. Both are soft operations — archived data is always recoverable.</p>

    <h3>Example Configuration</h3>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">config.toml</span></div>
      <pre><code dangerouslySetInnerHTML={{__html: `{\`[memory]

    </div>

  <section id="best-practices">
    <h2>Best Practices</h2>

    <h3>File-backed vs. Semantic Memory</h3>
    <p>
      The <code>memory</code> tool (file-backed CRUD) is best for deterministic operations —
      when you know the exact ID, need to update specific fields, or want to manage record
      lifecycle directly. The semantic tools (<code>memory_search</code>, <code>memory_absorb</code>,
      <code>memory_digest</code>) are best for discovery and knowledge ingestion — when you need
      to find relevant context, absorb new information, or generate summaries.
    </p>
    <div class="callout">
      <strong>Rule of thumb:</strong> Use <code>memory</code> for CRUD operations on known records.
      Use <code>memory_absorb</code> to store new facts and <code>memory_search</code> to find
      existing ones. Use <code>memory_digest</code> when you need a pre-assembled context block.
    </div>

    <h3>Structuring Facts for Search</h3>
    <p>Well-structured facts produce better search results. Follow these guidelines:</p>
    <ul class="check-list">
      <li><strong>Be self-contained</strong> — A fact should make sense without surrounding context. "The Series D was at $13.4B" is bad; "Plaid raised Series D at $13.4B valuation in April 2024" is good.</li>
      <li><strong>Include key entities</strong> — Mention company names, people, and dates explicitly. Embeddings and BM25 both rely on these signals.</li>
      <li><strong>One fact per record</strong> — Don't bundle multiple unrelated facts. Each record should capture a single atomic piece of knowledge.</li>
      <li><strong>Use descriptive keys</strong> — A key like <code>plaid-series-d-valuation</code> is more useful than <code>fact-42</code> for debugging and manual review.</li>
      <li><strong>Avoid duplicates</strong> — The absorb pipeline catches near-duplicates (cosine ≥ 0.85), but semantically different phrasings of the same fact may slip through. Rephrase consistently.</li>
    </ul>

    <h3>Distillation vs. Manual Management</h3>
    <p>
      Let distillation handle run-to-agent promotion automatically for most workloads. It ensures
      only meaningful facts survive and prevents memory bloat from transient session data.
      Use manual <code>memory add</code> when you need to seed the agent with baseline knowledge
      before a campaign — things like company profiles, product catalogs, or competitive intelligence
      that the agent should always know.
    </p>
    <ul class="check-list">
      <li><strong>Auto-distill</strong> — Enable <code>gc_auto = true</code> to distill after every session. Best for continuous research workflows.</li>
      <li><strong>Manual distill</strong> — Use <code>--dry-run</code> first to review what would be promoted, then run without the flag. Best for high-stakes campaigns where you want control.</li>
      <li><strong>Seed knowledge</strong> — Use <code>memory_absorb</code> with scope <code>agent</code> to pre-load facts before running research. This gives the agent a head start.</li>
    </ul>

    <h3>Tuning Garbage Collection</h3>
    <p>
      GC keeps the memory store healthy over time. The right settings depend on your usage pattern:
    </p>
    <table class="mini-table">
      <thead><tr><th>Workload</th><th>gc_ttl_days</th><th>gc_compact_above</th><th>Rationale</th></tr></thead>
      <tbody>
        <tr><td>High-volume research</td><td>14</td><td>100</td><td>Aggressive cleanup — lots of transient run data.</td></tr>
        <tr><td>Standard outreach</td><td>30</td><td>200</td><td>Balanced — the default works for most teams.</td></tr>
        <tr><td>Long-term accounts</td><td>90</td><td>500</td><td>Conservative — keep history for relationship building.</td></tr>
        <tr><td>Compliance / audit</td><td>365</td><td>1000</td><td>Minimal cleanup — retain everything for audit trails.</td></tr>
      </tbody>
    </table>

    <h3>Memory Hygiene</h3>
    <p>Periodic maintenance keeps your memory store accurate and useful:</p>
    <ul class="check-list">
      <li><strong>Review contradictions</strong> — Run <code>fathom memory list --scope agent</code> periodically and look for records linked by <code>contradicts</code> edges. Resolve them by boosting the correct one and archiving the stale one.</li>
      <li><strong>Audit importance scores</strong> — Facts with high importance that are no longer relevant will dominate digests. Use <code>memory_boost</code> to dial them back when context changes.</li>
      <li><strong>Prune stale run facts</strong> — If <code>gc_auto</code> is disabled, run <code>fathom memory gc --dry-run</code> weekly to check for accumulation.</li>
      <li><strong>Rebuild after model changes</strong> — Switching embedding models invalidates existing vectors. Always run <code>fathom memory rebuild --embeddings-only</code> after changing the <code>embeddings</code> config.</li>
      <li><strong>Monitor store size</strong> — Use <code>fathom memory stats</code> to track growth. A healthy store stays under 50MB for typical B2B outreach workloads.</li>
      <li><strong>Back up the database</strong> — The SQLite file at <code>db_path</code> contains everything. Include it in your backup rotation, especially before running <code>nuke</code>.</li>
    </ul>
  </section>
