    <h3>Скоринг уверенности</h3>
    <ul class="check-list">
      <li>База <strong>0.5</strong> — проверки синтаксиса, одноразовых и ролевых корректируют её.</li>

      <div class="step">
        <h3>1 · Экспорт</h3>
        <p>CSV, vCard, JSON или Excel через <code>fathom contacts export</code> — или более богатые отчёты сессии PDF/HTML/DOCX.</p>
      </div>
      <div class="step">
        <h3>2 · Отправка в CRM</h3>
        <p><code>fathom contacts push-crm</code> синхронизирует с amoCRM, Bitrix24 или HubSpot. Дедупликация по <code>crm_id</code> означает, что повторные запуски никогда не создают дубликаты.</p>
      </div>
      <div class="step">
        <h3>3 · Наблюдение за новыми лидами</h3>
        <p>Режим <code>watch</code> перезапускает тот же запрос каждые N секунд, сравнивает базу контактов и оповещает о новых строках.</p>

  <section id="verification-tools">
    <h2>Инструменты верификации подробно</h2>
    <p>
      Сырые данные зашумлены. Инструменты верификации очищают, нормализуют и скорят каждую запись
      контакта до её попадания в ваш пайплайн. Вот что делает каждый инструмент и как интерпретировать его вывод.
    </p>

    <div class="tool-card" id="verify-email">
      <div class="tool-card-header">
        <div class="tool-card-icon">✉️</div>
        <div>
          <h3 class="tool-card-name">verify_email</h3>
          <span class="tool-card-tag">5-стадийный пайплайн</span>
        </div>
      </div>
      <p>
        Самый критичный инструмент верификации. Каждый email проходит через пять последовательных стадий —
        каждая стадия может оборвать пайплайн при жёсткой ошибке (напр. невалидный синтаксис). Финальный
        скор уверенности — композит всех результатов стадий.
      </p>
      <h4>5-стадийный пайплайн в деталях</h4>
      <table class="mini-table">
        <thead><tr><th>Стадия</th><th>Что происходит</th><th>Влияние на скор</th></tr></thead>
        <tbody>
          <tr>
            <td><strong>1. Синтаксис</strong></td>
            <td>
              Валидация по подмножеству RFC 5322: ровно одна <code>@</code>, общая длина &le;254,
              локальная часть &le;64, без ведущих/двойных точек, TLD нечисловой и минимум 2 символа.
            </td>
            <td>Fail → 0.0 (жёсткая остановка)</td>
          </tr>
          <tr>
            <td><strong>2. MX-поиск</strong></td>
            <td>
              DNS-over-HTTPS через Google (основной) и Cloudflare (запасной). При отсутствии MX-записей
              возвращается к A-записи по RFC 5321 &sect;5.1.
            </td>
            <td>Резолвится → +0.4; NXDOMAIN → 0.1 (жёсткая остановка)</td>
          </tr>
          <tr>
            <td><strong>3. Одноразовые</strong></td>
            <td>
              Проверяет домен по ~50 известным временным провайдерам: mailinator, yopmail,
              guerrillamail, tempmail, 10minutemail и т.д.
            </td>
            <td>Совпадение → &minus;0.3</td>
          </tr>
          <tr>
            <td><strong>4. Ролевые</strong></td>
            <td>
              Помечает департаментские / noreply-адреса: <code>info@</code>, <code>sales@</code>,
              <code>support@</code>, <code>admin@</code>, <code>no-reply@</code>, <code>billing@</code> и т.д.
            </td>
            <td>Совпадение → &minus;0.15 (всё ещё используемый, но с меньшим приоритетом)</td>
          </tr>
          <tr>
            <td><strong>5. SMTP-проба</strong></td>
            <td>
              Опционально (<code>smtp_check=true</code>). Открывает TCP:25, отправляет <code>HELO</code>,
              <code>MAIL FROM</code>, <code>RCPT TO</code>. Принимает 250/251 как доставляемый, 5xx как
              отклонённый. <strong>Никогда не отправляет DATA</strong> — реальное письмо не доставляется.
            </td>
            <td>Принят → &ge;0.95; Отклонён → &le;0.2; Таймаут → ограничено 0.9</td>
          </tr>
        </tbody>
      </table>

      <h4>Алгоритм скоринга уверенности</h4>
      <div class="code-block">
        <div class="code-header"><span class="code-lang">python</span></div>
        <pre><code set:html={`score = 0.5                                    # база
if mx_resolved:     score += 0.4               # домен реальный
if disposable:      score -= 0.3               # временный домен
if role_based:      score -= 0.15              # департаментский ящик
if smtp_accepted:   score = max(score, 0.95)   # сервер подтвердил
if smtp_rejected:   score = min(score, 0.2)    # сервер отклонил
if no_smtp_check:   score = min(score, 0.9)    # нельзя полностью подтвердить
score = clamp(score, 0.0, 1.0)
if pattern_matched: score = min(score + 0.15, 0.95)  # бонус suggest_emails`} /></pre>

    <h2>Рабочий процесс управления контактами</h2>
    <p>
      Каждый контакт, обнаруженный пайплайном, проходит через единый слой управления на SQLite.

    <p>

      Схема спроектирована для быстрой дедупликации и гибких метаданных.
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">sql</span></div>
      <pre><code set:html={`CREATE TABLE contacts (
    id          TEXT PRIMARY KEY,   -- UUID v4
    name        TEXT,
    email       TEXT,
    phone       TEXT,
    title       TEXT,
    company     TEXT,
    linkedin    TEXT,
    twitter     TEXT,
    github      TEXT,
    website     TEXT,
    location    TEXT,
    bio         TEXT,
    confidence  REAL DEFAULT 0.0,
    source_url  TEXT,
    crm_id      TEXT,               -- устанавливается после отправки в CRM
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE UNIQUE INDEX idx_dedup
    ON contacts(email, phone, linkedin);`} /></pre>
    </div>
    <h4>Логика дедупликации</h4>
    <ul class="check-list">
      <li><strong>Первичный ключ:</strong> композитный email + phone + LinkedIn. Если любые два из трёх совпадают, запись сливается.</li>
      <li><strong>Стратегия слияния:</strong> непустые поля из более новой записи перезаписывают старые пустые поля; уверенность берётся большее значение.</li>
      <li><strong>Нормализация имён:</strong> диакритика убирается, пробелы схлопываются, сравнение без учёта регистра.</li>
    </ul>

      Извлекает email, номера телефонов и URL соцпрофилей из свободного текста, сырого HTML или живого URL.
      Обрабатывает обфусцированные паттерны вроде <code>bob [at] acme [dot] com</code> и контент,
      отрисованный JavaScript.

  <section id="approval-flow">
    <h2>Процесс подтверждения подробно</h2>
    <p>
      Не каждый инструмент должен выполняться без проверки человеком. Процесс подтверждения закрывает
      операции с побочными эффектами — так что агент может свободно планировать, но ему нужно ваше явное
      «да» перед записью в вашу CRM, сохранением контактов или пушем кода.
    </p>

    <h3 id="gated-tools">Закрытые инструменты (по умолчанию)</h3>
    <table class="mini-table">
      <thead><tr><th>Инструмент</th><th>Почему закрыт</th></tr></thead>
      <tbody>
        <tr>
          <td><code>save_contacts</code></td>
          <td>Пишет в <code>contacts.db</code> и опционально отправляет в CRM — реальные побочные эффекты</td>
        </tr>
        <tr>
          <td><code>git_push</code></td>
          <td>Пушит код в удалённый репозиторий — необратимо после публикации</td>
        </tr>
      </tbody>
    </table>

    <h3 id="customize-approval">Как настроить</h3>
    <p>
      Добавляйте или убирайте закрытые инструменты в <code>config.toml</code> в секции <code>[agent]</code>:
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">toml</span></div>
      <pre><code set:html={`[agent]
# По умолчанию: save_contacts и git_push требуют подтверждения
approval_tools = ["save_contacts", "git_push"]

# Добавить больше инструментов под защиту:
approval_tools = ["save_contacts", "git_push", "send_email", "crm_push"]

# Убрать все защиты (используйте осторожно):
approval_tools = []`} /></pre>
    </div>

    <h3 id="tui-approval">Процесс подтверждения в TUI</h3>
    <ul class="check-list">
      <li>Агент приостанавливается и показывает сводку ожидающего действия в терминальном UI.</li>
      <li>Вы видите: имя инструмента, параметры, ожидаемый результат и любые предупреждения.</li>
      <li>Нажмите <code>y</code> для подтверждения, <code>n</code> для отказа или <code>e</code> для редактирования параметров перед подтверждением.</li>
      <li>Редактирование открывает JSON параметров в вашем <code>$EDITOR</code> для встроенного изменения.</li>
    </ul>

    <h3 id="api-approval">Процесс подтверждения через API</h3>
    <p>
      При headless-запуске или интеграции в CI/CD подтверждайте через REST API:
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">bash</span></div>
      <pre><code set:html={`# Подтвердить ожидающее действие
curl -X POST http://localhost:8080/api/v1/sessions/sess_abc123/approve \\\\
  -H "Content-Type: application/json" \\\\
  -d '{"action_id": "act_789", "approved": true}'

# Отклонить ожидающее действие
curl -X POST http://localhost:8080/api/v1/sessions/sess_abc123/approve \\\\
  -H "Content-Type: application/json" \\\\
  -d '{"action_id": "act_789", "approved": false}'`} /></pre>
    </div>

    <h3 id="timeout-fallback">Поведение по таймауту и запасной вариант</h3>
    <p>
      Если подтверждение не пришло в настроенное окно, агент использует запасную стратегию:
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">toml</span></div>
      <pre><code set:html={`[agent]
# Что делать при истечении времени подтверждения:
# "deny"  — пропустить действие, продолжить пайплайн
# "allow" — автоматическое подтверждение (для полностью автоматизированных запусков)
# "pause" — приостановить сессию, возобновить позже
approval_fallback = "deny"

# Таймаут в секундах (по умолчанию: 300 = 5 минут)
approval_timeout_seconds = 300`} /></pre>
    </div>
    <div class="callout">
      <div class="callout-icon">⚠️</div>
      <div class="callout-content">
        <strong>Никогда не устанавливайте <code>approval_fallback = "allow"</code> в проде</strong>,
        если только вы не запускаете полностью автоматизированный пайплайн со строгой валидацией параметров.
        Автоподтверждение обходит проверку человеком для записей в CRM и пушей кода.
      </div>
    </div>
  </section>

  <section id="watch-mode">
    <h2>Режим watch и мониторинг</h2>
    <p>
      Режим watch превращает разовую задачу аутрича в повторяющийся монитор. Перезапускайте тот же запрос
      по расписанию, сравнивайте результаты и получайте уведомления только при появлении новых контактов.
    </p>

    <h3 id="repeat-flag">Флаг --repeat</h3>
    <p>
      Добавьте <code>--repeat N</code> для перезапуска каждые <code>N</code> секунд. Агент выполняет полный
      пайплайн на каждом цикле — но сохраняет только контакты, которые новы или изменились с последнего запуска.
    </p>
    <div class="code-block">
      <div class="code-header"><span class="code-lang">bash</span></div>
      <pre><code set:html={`# Перезапуск каждые 24 часа (86400 секунд)
fathom run "Find new VP Engineering hires at Series B startups in SF" \\\\
  --repeat 86400`} /></pre>
    </div>

    <h3 id="diff-detection">Как работает обнаружение различий</h3>
    <ul class="check-list">
      <li>Каждый запуск делает снапшот состояния базы контактов (хэш email + phone + LinkedIn).</li>
      <li>Перед сохранением новые записи сравниваются с предыдущим снапшотом.</li>
      <li>Только по-настоящему новые или обновлённые контакты вызывают уведомления.</li>
      <li>Удалённые контакты (присутствующие в снапшоте, отсутствующие в новом запуске) логируются, но не удаляются.</li>
    </ul>

    <h3 id="notification-channels">Каналы уведомлений</h3>
    <div class="steps">
      <div class="step">
        <h3>Вебхук</h3>
        <p>
          POST JSON-полезной нагрузки на любой URL. Настраивается через переменную окружения
          <code>NOTIFY_WEBHOOK_URL</code>. Полезная нагрузка включает число новых контактов, детали
          контактов и метаданные запуска.
        </p>
      </div>
      <div class="step">
        <h3>Email</h3>
        <p>
          Отправка дайджест-письма через SMTP. Настройте <code>SMTP_HOST</code>, <code>SMTP_PORT</code>,
          <code>SMTP_USER</code>, <code>SMTP_PASS</code> и <code>NOTIFY_EMAIL_TO</code>.
        </p>
      </div>
      <div class="step">
        <h3>Telegram</h3>
        <p>
          Отправка сообщения в чат Telegram через Bot API. Установите переменные окружения
          <code>TELEGRAM_BOT_TOKEN</code> и <code>TELEGRAM_CHAT_ID</code>.
        </p>
      </div>
    </div>
